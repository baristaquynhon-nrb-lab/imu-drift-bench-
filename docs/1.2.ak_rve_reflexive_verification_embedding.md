## 1.2.ak.1 Purpose

Current VTS suites exist as external tools that evaluate CAS from outside.
RVE transforms verification into an internal epistemic event:

```
Verification → Epistemic Event → CLP append → History axis H
```

> Central claim: Every valid CAS verification must be representable as an event
> in the CLP chain, making the system a reflexive epistemic system.

---

## 1.2.ak.2 Extension of Epistemic State

Extend the manifold from:

```
E = (M, L, X, C, H)
```

to:

```
E* = (M, L, X, C, H, V)
```

Where V = Verification trace manifold. Each point in V contains:

| Field | Meaning |
|-------|---------|
| spec_hash | SHA-256 of spec file |
| runner_hash | SHA-256 of test runner |
| case_hash | SHA-256 of test vectors |
| result_hash | SHA-256 of output artifact |
| verdict | PASS / FAIL / REFUSE |
| timestamp | Logical CLP time |
| layer_ref | Section tested (1.2.ag, 1.2.ah, ...) |

```json
  "spec_hash": "sha256:...",

```

Pipeline: VTS → JSON result → Canonicalization → CLP append

## 1.2.ak.4 History Axis Integration

History axis H stores verification events in sequence:

```
H = (..., VTS_event_1, VTS_event_2, ...)
```

Hash chain integrity:

```
CLP_HASH_t = hash(CLP_HASH_{t-1} || canonical_event_t)
```

VTS events become cryptographic witnesses in the chain.

## 1.2.ak.5 Replay Verification Protocol

To verify a CAS session:

1. Extract all VERIFICATION_EVENT from chain
2. Retrieve spec_hash, runner_hash, case_hash
3. Rebuild verification environment
4. Rerun runner with case vectors
5. Compare: new_result_hash == stored_result_hash
6. Match → verification is replay-valid
